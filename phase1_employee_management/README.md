## Technical Interview Q&A (Real-World Experience)

#### Q1: Why should we use `GENERATED BY DEFAULT AS IDENTITY` instead of legacy sequences/triggers for primary keys in Oracle 12c+?
**Answer:** 
In legacy Oracle databases (11g and older), auto-generating primary keys required creating a standalone Sequence object and a `BEFORE INSERT` database trigger to assign the sequence value to the column. This was highly inefficient:
1. **Context Switching:** Every single row insert triggered a context switch between the SQL engine and the PL/SQL trigger engine.
2. **Serialization:** Triggers serialize inserts under heavy concurrent load, causing latch contention on the sequence object.

Oracle 12c introduced identity columns (`GENERATED AS IDENTITY`). These are backed by native metadata-linked sequences. Under the hood, Oracle fetches sequence values directly within the SQL insert block, bypassing trigger execution entirely. This results in **30-50% faster batch inserts** and removes clutter from the database schema.

#### Q2: What is the classic NULL trap when using `GROUP BY` and aggregate functions like `AVG` or `COUNT`?
**Answer:**
Aggregate functions (except `COUNT(*)`) ignore `NULL` values. This causes silent calculation bugs:
1. **The average salary bug:** If you have 5 employees in a department with salaries `[1000, 2000, NULL, NULL, NULL]`, running `AVG(salary)` will return `1500` (which is `(1000+2000)/2`). The CBO ignores the 3 employees with `NULL` salaries. However, the true average salary across the department's headcount is `600` (`3000 / 5`).
2. **The solution:** You must force aggregate functions to recognize nulls as zero by wrapping them in `NVL` or `COALESCE` first:
   ```sql
   SELECT AVG(NVL(salary, 0)) AS real_average FROM employees;
   ```
3. **COUNT Trap:** `COUNT(commission_pct)` counts only rows where the commission is not null. `COUNT(*)` counts every row. Interviewers will test if you understand that aggregate calculations change depending on whether you pass a column name or an asterisk.
